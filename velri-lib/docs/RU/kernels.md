# Архитектура кернелов: Slang-first (`slangc` AOT для GPU и CPU)

[English](../EN/kernels.md)

Вместо раздельного сопровождения GLSL-шейдеров, `#ifdef`-комбинаций и дублирующихся ручных SIMD-файлов под каждую архитектуру CPU целевая система кернелов `Velri-lib` строится вокруг **Khronos Slang** (`Apache-2.0 WITH LLVM-exception`) с **чистой AOT-компиляцией через `slangc` при сборке**.

**Статус:** целевой дизайн + прототип модульных Slang-кернелов в `velri-lib/src/kernels/slang/`. Работающий нативный C23/SIMD-набор `VelriLib::cpu` ([cpu-kernels.md](cpu-kernels.md)) служит рабочей базой (Этап 0) и контрольной планкой по скорости и точности при переходе на Slang CPU.

---

## 1. Главные принципы: переиспользование компонентов и никаких дублей

1. **Маленькие переиспользуемые компоненты вместо монолитных копий:** общая математика раскладывается на интерфейсы и дженерики Slang (`IElement`, `IActivation`, `IEpilogue`, `IKVSource`, общие редукции). Одна реализация `RMSNorm`, `RoPE`, `GatedMLP` или `Linear` переиспользует эти компоненты вместо копипасты.
2. **Не плодим почти одинаковые кернелы:**
   - **Никаких отдельных исходников для AVX2 и AVX-512** (или для `F32`/`F16`/`BF16`): один параметризованный `.slang`-модуль AOT-компилируется `slangc` под нужные целевые профили (`base`, `avx2`, `avx512`, `aarch64`, `riscv64`, `spirv`).
   - Аппаратные отличия (например, редукция по подгруппе на GPU против скалярного/векторного цикла на CPU, или `CoopMat` на GPU) изолируются внутри тонких низкоуровневых примитивов, а не размножают целые кернелы.
3. **Чистый AOT (`slangc` при сборке) — `0` компиляторов в рантайме:** готовый бинарь Velri не зависит от `libslang`, LLVM, `shaderc`, Python или PyTorch.

```text
src/kernels/slang/
  ├── common/ (numeric, activations, epilogue, reductions)
  └── ops/    (norm, rope, elementwise, linear, ...)
        │
        ├──► slangc -target spirv      ──► .spv (+ spirv-val)       ──► Vulkan-бэкенд
        ├──► slangc -target llvm-ir/o  ──► .o (ISA-варианты CPU)    ──► CPU-бэкенд (velri_pool)
        └──► slangc reflection         ──► таблицы привязок CMake
```

## 2. Модульная композиция в Slang

Принципы композиции Velri выражаются напрямую в типах Slang, без ветвлений по имени модели:

- **`IElement` (`common/numeric.slang`):** единый доступ к `F32`, `F64`, `FP16`, `BF16`, `INT8` (загрузка/преобразование в накопитель и запись обратно) — операции не дублируются по типам.
- **`IActivation` (`common/activations.slang`):** `SiLU`, `GELU_tanh`, `ReLU2`, `Identity` (+ опциональный симметричный `clamp`) — переиспользуются одновременно в standalone-активациях, `GatedMLP` и эпилогах `Linear`.
- **`IEpilogue` (`common/epilogue.slang`):** добавление `bias`, масштабирование (`W8A8` / `W8A32`) и опциональная активация — общие для `GEMV` и `GEMM` на CPU и GPU.
- **`IKVSource`:** источник ключей и значений для attention — раздельные буферы, общий буфер или восстановление на лету `K = RoPE(V * w_k)` (Gemma 4) без лишнего буфера `K`.
- **AOT-слияния (fusion):** горячие связки (`Residual + RMSNorm`, `GatedMLP`, `Linear + Epilogue`, `K=V + Attention`) собираются как AOT-специализации тех же интерфейсов из контролируемого манифеста CMake.
- **Autodiff (`bwd_diff`):** встроенная возможность Slang, доступная при необходимости для будущих инструментов квантования/калибровки без переписывания математики.

## 3. GPU-путь: Vulkan / SPIR-V и переносимость на другие GPU

- **Базовый профиль:** Vulkan 1.1 compute со стандартными storage buffers и явной проверкой возможностей устройства до выбора кернела.
- **Ускоренные пути (SPIR-V 1.5/1.6):** `linalg::CoopMat` (`SPV_KHR_cooperative_matrix`, FP16/BF16/INT8), `VK_KHR_shader_bfloat16`, `VK_KHR_shader_float16_int8`, `VK_KHR_shader_integer_dot_product` и subgroup-операции включаются **только при подтверждённой поддержке устройством**.
- **Раздельные проверки возможностей:** хранение, арифметика и накопление проверяются независимо; фиксированный размер subgroup (32 или 64) не зашивается как допущение.
- **Валидация при сборке:** каждый `.spv` проверяется `spirv-val` под целевой профиль Vulkan в CMake и CI.
- **Управление pipelines:** выбор AOT-специализаций и создание `VkPipeline` происходят в `prepare`; совместимость дискового pipeline cache проверяется по устройству и драйверу.
- **Переносимость на будущие GPU API:** те же `.slang`-модули в перспективе компилируются в **Metal (MSL)**, **CUDA**, **DXIL** и **WGSL** за тонкими device-бэкендами в `src/backend/<name>/` без переписывания математики.

## 4. CPU-путь: Slang-first и план доработок Slang CPU-бэкенда

### Роль Slang и C23 на CPU
Целевой курс для CPU — **Slang-first для всех оптимизированных кернелов** из общей модульной базы. На чистом **C23** остаются:
- публичный API, граф, планировщик памяти и реестр бэкендов;
- постоянный пул рабочих потоков `velri_pool` и L3-планировщик;
- **простые независимые C23-эталоны** для проверки корректности без участия компилятора Slang.

### Ограничения Slang CPU из коробки и стратегия доработок
Slang умеет выдавать CPU-код через LLVM (`slang-llvm`: LLVM IR / `.o`) и C++. На практике мы учитываем реальные ограничения:
1. В C++-бэкенде нет workgroup-барьеров (`GroupMemoryBarrierWithGroupSync`) и пользовательских атомиков — алгоритмы с `groupshared`-синхронизацией напрямую на CPU не переносятся.
2. Стандартная C++-обвязка слишком тяжела для коротких вызовов из C23 `velri_pool`; для CPU нужен прямой путь через **LLVM IR / `.o` с чистым C-ABI** и `0 B` аллокаций в куче.
3. Один и тот же Slang-исходник компилируется в целевой LLVM IR, а затем **флагами таргета компилятора** (`-march=x86-64`, `-mavx2 -mfma -mf16c`, `-mavx512f -mavx512bw ...`, `aarch64`, `riscv64`) получаются ISA-варианты — **без копирования кода под AVX2 и AVX-512**.
4. Для горячего CPU `GEMM` / `GEMV` критичны регистровый тайлинг, перепаковка панелей в `scratch` и аппаратные dot-инструкции (`vdpbf16ps`, `vpdpbusd`). Если стандартный CPU-бэкенд Slang не вытягивает нужный кодген, мы фиксируем конкретный разрыв по замерам и точечно дорабатываем CPU-бэкенд Slang (чистый C-ABI, `fp16`/`bf16`, векторные примитивы / интринсики).

### Проверенные результаты и ограничения Slang `2026.22.1` (эмпирика прототипа)
Сборка прототипа включается опциями CMake `-DVELRI_ENABLE_SLANG_CPU=ON` и `-DVELRI_ENABLE_VULKAN=ON` (`entry_cpu.slang`, `entry_vulkan.slang`, бенчмарки `bench_slang_cpu` и `bench_vulkan`). На `slangc 2026.22.1` подтверждены оба целевых пути из общих модулей `common/` и `ops/`:
- **CPU (`-target host-object-code -O3 -fp-mode fast`):** чистый C-ABI (`[DllExport] export __extern_cpp`) без runtime-зависимостей; единый исходник `linear_cpu.slang` компилируется под `base`/`avx2`/`avx512` через `-DVELRI_MR/NR_F32/NR_F64` без дублей. Ключевые приёмы под `slang-llvm`:
  - `pack_b` через `IElement::load4F32` + выровненные записи `Ptr<float4>`/`Ptr<double4>` (убирает `vgather`/`vscatter`), плюс zero-copy чтение `A` для нативных `F32`/`F64` (убирает `call memcpy` от `LoopIdiomRecognize`);
  - точный по модулю $2^{32}$ `W8A8` на микрокернеле `F32` при `KC=128` ($|\sum| \le 2^{21} \ll 2^{24}$);
  - одноцикловые редукции через `select(v > m, v, m)` (обычные `max()` и `?:` под `-fp-mode fast` генерируют `vucomiss` и ломают векторизацию; `select` даёт 4-way ZMM `vmaxps`), Radix-4 Stockham ping-pong для FWHT без алиасинга и запись в локальные буферы строго через `Ptr` (обход SSA-особенности локальных массивов Slang).
- **Vulkan (`-target spirv -profile spirv_1_6 -fvk-use-c-layout -O3`):** под C-layout Slang по умолчанию ставит `Aligned 4` на BDA-указатели (`4× LDG.32`), поэтому критичны явные хелперы `OpLoad`/`OpStore Aligned 16` (`LDG.128`/`STG.128`), `ks=0 / BAR / STS.128 + ks=1` перекрытие для однобуферного `CoopMat` (`20 KiB` -> `2 WG/SM`) и `Split-K` (`vk_splitk_reduce`) для малых батчей `F32`.
- **Два оставшихся ограничения `slang-llvm` (фронт доработки CPU-бэкенда Slang):**
  1. **`BFloat16` не поддерживается на LLVM-таргете** (`InternalError: Unsupported type for LLVM target!`) — используется побитовый `ElemBF16` (`uint16_t`), без генерации `vdpbf16ps` (`AVX512_BF16`).
  2. **`dot4add_i8packed` и целочисленный dot на CPU не опускаются в `vpdpbusd` (`AVX512_VNNI`)** — W8A8 упирается в потолок FP32 FMA (`~4.0 TOPS` против `~8.7 TOPS` `VelriLib::cpu` с VNNI).

### Правило замены текущего C23-кода
Работающие сейчас нативные ядра [VelriLib::cpu](cpu-kernels.md) **не удаляются авансом**. Slang CPU-кернел заменяет нативный путь только после того, как:
- проходит все контрактные тесты (хвосты, шаги, guard pages, ASan/UBSan, AArch64/RISC-V QEMU);
- подтверждает сопоставимую или лучшую полную скорость вызова по [правилам измерений](../../../docs/RU/performance.md).

## 5. Численные контракты и верификация

- **Валидация до первой записи:** размеры, шаги, переполнения, выравнивание и запрещённые пересечения проверяются до изменения выхода; `rows == 0` ничего не пишет.
- **Нулевые аллокации на горячем пути:** рабочая память `scratch` запрашивается в `prepare`.
- **Вещественные операции (`F64`, `FP32`, `FP16`, `BF16`):** разрешены FMA, несколько аккумуляторов, блочные редукции и полиномиальные приближения; побитовое совпадение между ISA и CPU/GPU не требуется — проверяются явные допуски против C23-эталона.
- **Целочисленные и точные операции (`INT8`, индексы):** детерминированный контракт (`INT8 Linear` накапливает по модулю $2^{32}$ без signed-overflow UB).
- **Защита границ и валидация:** независимый C23-эталон + ASan/UBSan + `guard pages` для CPU-кода; `spirv-val` + Vulkan API/sync validation layers для GPU.
