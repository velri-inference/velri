# W8A8 на 64 последовательных токенах TinyLlama

[English](README.EN.md)

24 ноября 2026 года. Один запрос, batch=1, 128 токенов промпта, 64 зависимых шага с greedy sampling. На Ryzen 9 9950X проекции W8A8 достигли 91,57% измеренного потолка памяти с AVX2 и 91,14% с AVX-512. На RTX 5070 Ti через Vulkan результат составил 76,69%. До целевых 90% на GPU осталось 13,31 процентного пункта. [Таблицы всех задействованных кернелов](OPERATORS.md) · [Полные данные в CSV](operators.csv)

## Время генерации

| Бэкенд | Три запуска до, мс | Три запуска после, мс | Среднее до → после, мс | Ток/с до → после | Снижение времени | Потолок только по весам, ток/с | Δ после к нему |
|---|---|---|---:|---:|---:|---:|---:|
| 9950X, 16 ядер, AVX2 | 1127,36 / 1138,86 / 1128,11 | 1044,26 / 1052,13 / 1047,72 | 1131,44 → 1048,04 | 56,57 → 61,07 | 7,37% | 66,98 | −8,83% |
| 9950X, 16 ядер, AVX-512 | 1126,37 / 1144,36 / 1148,54 | 1069,18 / 1066,35 / 1058,31 | 1139,76 → 1064,62 | 56,15 → 60,12 | 6,59% | 68,04 | −11,65% |
| RTX 5070 Ti, Vulkan | 124,79 / 126,32 / 120,12 | 113,85 / 112,13 / 114,96 | 123,75 → 113,64 | 517,18 → 563,16 | 8,16% | 808,97 | −30,39% |

Каждая ячейка с тремя временами — три отдельных процесса. Каждый раз движок загружал одни и те же веса, выполнял два полных прогрева и засекал следующую генерацию. Порядок пар — до/после, после/до, до/после. Время включает все 64 обращения к публичной `velri_session_step`, ожидание устройства, возврат логитов и выбор следующего токена. Подготовка, префилл и запись контрольных логитов происходили вне измеряемого интервала. Скорость равна 64 000, делённым на среднее время в мс. Процессы имели маску CPU 0–15, по одному логическому CPU на физическое ядро. Частоты управлялись автоматически. [Исходная методика](../../../tools/decode64-method.md) · [Времена, калибровки и исходники контрольных замеров](session-evidence.tar.gz)

## Как получены потолки

| Бэкенд | Измеренный пик INT8, TOPS | Измеренный пик FP32, TFLOPS | Полоса длинного чтения, GB/s | Номинальная полоса интерфейса, GB/s |
|---|---:|---:|---:|---:|
| 9950X, AVX2 | 4,779 | 2,760 | 69,400 | 96 |
| 9950X, AVX-512 | 22,193 | 5,540 | 70,500 | 96 |
| RTX 5070 Ti | 393,425 | 47,410 | 838,196 | 896 |

Вычислительный пик — среднее по трём запускам независимых регистровых тестов на этой машине. На CPU использовались FP32 FMA, расширение пар INT8 для AVX2 и VNNI для AVX-512. На GPU использовались плотные INT8 Tensor Core MMA и FP32 FMA. Шейдер W8A8 для одного токена использует упакованный INT8 dot на SM. Дополнительная калибровка именно этой инструкции (восемь независимых цепочек DP4A в регистрах, три запуска, машинная инструкция IDP.4A.S8.S8) дала 97,670 TOPS. Фактические 1,280 TOPS проекций отстают от неё на 98,69%. Даже для DP4A предел чтения этих форм остаётся 1,669 TOPS. Длинное чтение измерено на буферах 1 GiB в RAM и 512 MiB в VRAM. На стенде установлены два канала DDR5-6000 шириной 64 бита, у видеокарты — 256-битная GDDR7 на 28 Гбит/с на вывод. PCIe 5.0 ×16 измерен отдельно по переносу 64 MiB из GPU в закреплённую память хоста, среднее 57,807 GB/s. Для 128 000 байт логитов тот же тест дал 46,894 GB/s. [Код и все три измерения](session-evidence.tar.gz) · [Спецификация NVIDIA Blackwell, таблица 5](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf)

Для умножения матрицы M×K на один вектор считаем 2MK полезных операций. Потолок для каждой формы — минимум вычислительного пика и полосы памяти, умноженной на отношение операций к минимальному логическому трафику. Потолок только по весам в первой таблице предполагает одно чтение 1 034 420 224 байт INT8-весов и 1 704 960 байт FP32-масштабов за токен. Attention, KV-кеш, остальная арифметика и синхронизация добавляют время. Этим объясняется разница между процентом для проекций и процентом для всей сессии. [Формулы учёта по операциям](../../../tools/profile/README.md)

| Проекции W8A8 вместе | Факт до → после, TOPS | Δ после к вычислительному пику | Потолок форм после, TOPS | Доля потолка форм до → после | Δ после к потолку форм |
|---|---:|---:|---:|---:|---:|
| AVX2 | 0,1273 → 0,1266 | −97,35% | 0,1383 | 92,08% → 91,57% | −8,43% |
| AVX-512 | 0,1252 → 0,1280 | −99,42% | 0,1405 | 89,10% → 91,14% | −8,86% |
| Vulkan | 1,1628 → 1,2799 | −99,67% | 1,6690 | 69,63% → 76,69% | −23,31% |

Взвешенная строка делит полную работу на суммарное время всех диспетчей, содержащих проекцию. В профиле AVX2 суммарное время проекций выросло на 0,55%, хотя штатный запуск ускорился во всех трёх парах. Пооператорные прогоны и прогоны полной сессии выполнялись отдельно. На GPU диагностические барьеры сериализуют команды, исходная и итоговая пустые пары меток занимали около 0,3 мкс. Поэтому сумма времён GPU-профиля может превышать штатное время генерации. [Трассы, таблицы и код диагностики](operator-evidence.tar.gz)

## Изменения и оставшиеся ограничения

Полный TinyLlama-1.1B-Chat-v1.0 содержит 22 слоя, ширину 2048, MLP 5632, 32 Q-головы и 4 KV-головы шириной 64. Независимая выходная матрица имеет 32 000 строк. Бенчмарк создаёт дескриптор W8A8 существующей публичной функцией `velri_model_create_synthetic`, передаёт обученные знаковые INT8-веса и масштабы через `velri_model_bind_weight` и вызывает `velri_program_prepare`. Граф квантует 89 строк активаций за токен, по четыре в каждом из 22 слоёв и одну перед выходной головой. Q/K/V используют общий результат, как и gate/up. Эмбеддинги, нормы и KV-кеш в этом запуске имеют тип FP32. У проекций этого чекпойнта нет смещений. Исполняются все 155 проекций, включая голову. [Исходный чекпойнт](https://huggingface.co/TinyLlama/TinyLlama-1.1B-Chat-v1.0/tree/fe8a4ea1ffedaf415f4da2f062534de366a451e6)

**CPU.** В штатном плане W8A8 использует построчные веса. Для длинных проекций с более чем 128 KiB весов на исполнителя C23-кернел теперь дочитывает каждую строку целиком. Четыре крупные формы достигли 90,4–93,3% потолка. Самая короткая K/V 256×2048 занимает 9,81 мкс на AVX2 и 9,74 мкс на AVX-512, или 77,60% и 76,95%. Даже простое чтение этой полумегабайтной матрицы через тот же пул занимало 8,22 мкс. Для 90% нужны 8,46 и 8,33 мкс соответственно. Один пустой вызов 16 исполнителей после K/V в реальном decode занял в среднем 0,637 и 0,680 мкс, по 2816 наблюдений. Замер чтения уже включает такую диспетчеризацию. Объединение соседних проекций дало 2,48% и 1,09% по времени всей сессии в отдельном эксперименте с пересекающимися диапазонами запусков. В коммит вошло изменение обхода строк. [Пооператорные результаты](OPERATORS.md) · [Контрольные измерения](session-evidence.tar.gz)

**Vulkan.** Один диспетч теперь выполняет Q/K/V с RoPE, другой — gate/up с SiLU. При совместимых расположениях буферов сложение с остатком выполняется в конце проекции, а квантизация строки 5632 повторно использует значения из регистров. Самостоятельный A/B замер QKV и gate/up дал 127,32 → 120,51 мс за 64 токена. Расширение регистровой ветки квантизации дало 121,23 → 116,48 мс в серии из пяти процессов на версию. Отдельное сравнение последнего объединения с остатком дало 112,27 → 111,48 мс за три пары, с выигрышем в одной паре из трёх. Эффекты пересекаются, отдельный выигрыш этого объединения меньше разброса запусков. Наибольшая матрица 32000×2048 достигла 95,84% потолка. Меньшие объединённые диспетчи достигли 56,62% для выходной проекции attention со встроенной квантизацией и остатком, 61,80% для QKV с RoPE, 74,95% для down с остатком и 85,72% для gate/up с SiLU. [Все времена и формы](OPERATORS.md)

Чтобы отделить стоимость чтения от арифметики, в обычный Vulkan command buffer добавили диспетчи на вторую холодную копию всех W8-матриц, сохранив исходный путь генерации и его результаты. После вычитания варианта с нулевой сеткой дополнительный точный W8A8 занял 90,41 мс за 64 шага, чтение тех же весов с контрольной суммой — 90,34 мс. Разница 0,07 мс меньше разброса трёх пар. На веса это 732,25 и 732,83 GB/s, или около 87,4% широкой потоковой калибровки. Независимое холодное чтение тех же размеров через CUDA выявило зависимость от объёма одного запуска. Один диспетч читал 0,5 MiB со скоростью 288 GB/s, 4 MiB — 668 GB/s, 11 MiB — 762 GB/s, матрицу головы — 822 GB/s. Взвешенное по числу матриц время такого чтения за все 64 токена составило 91,83 мс. В пооператорном Vulkan-профиле проекции заняли 103,45 мс при бюджете 88,15 мс для 90%. Оставшийся разрыв в этом профиле — 15,30 мс. Контроль показывает цену коротких чтений и расписания на данном пути, универсальность такого предела для других реализаций этим экспериментом не установлена. [Парные эксперименты и воспроизведение](OPERATORS.md) · [Независимое чтение тех же форм](session-evidence.tar.gz)

## Проверка чисел и переносимости

На каждом бэкенде исходная и новая версии дали побайтно одинаковые 65 × 32 000 FP32-логитов. Все 18 процессов выдали одну и ту же последовательность ID, FNV-1a64 `8a5348dd784b27aa`. Между бэкендами есть различия в значениях логитов. Независимый PyTorch/Hugging Face эталон по исходному чекпойнту, с подачей одинаковой истории, совпал по 65 из 65 argmax. Для FP32 на AVX-512 относительная L2-ошибка равна 0,00000301, максимальная абсолютная 0,000117. Независимый W8A8-эталон на PyTorch CUDA использует целочисленно точную сумму в FP64 и единое правило округления точных половин от нуля. Относительная L2-ошибка составила 0,05242 для AVX2, 0,05169 для AVX-512 и 0,05203 для Vulkan. Максимальная абсолютная ошибка составила 1,04658 / 1,08739 / 1,14634 соответственно. Это расхождение существенно для сравнения логитов, даже когда выбранные токены совпадают. На фактических CPU-входах в каждой ISA проверены 1 015 713 выходов скалярного произведения и 48 899 584 кода активаций, все совпали с покомпонентным эталоном. По 16 707 проверенным масштабам максимальная относительная разница составила 1,20×10⁻⁷. [Эталонная реализация](../../../tools/check_session_reference.py) · [Логи проверок](session-evidence.tar.gz)

В Release на стенде прошли все шесть тестов. Шейдеры также проверены через llvmpipe. Сборки с базовым CPU и с отключённым C23-ускорением прошли по шесть тестов. Под QEMU проверены AArch64 Cortex-A53, RV64 SiFive U54 и AVX2 Haswell без VNNI. Windows x64 прошёл шесть тестов под Wine 10. Для Android arm64-v8a и x86_64 собраны бенчмарк и тесты CPU/Vulkan с NDK r29, API 28. На устройствах Android скорость и корректность не измерялись. Движок также прошёл четыре интеграционных теста с отдельно установленной VelriLib 0.7.0. Пакет 0.6.0 не создаёт нужные W8A8-масштабы, поэтому сборка с внешней библиотекой запрашивает новую версию. Измерения пропускной способности относятся к физическим 9950X и RTX 5070 Ti. [Результаты тестов](session-evidence.tar.gz)

## Как повторить

Команды рассчитаны на Linux, Clang с C23, Slang, Vulkan SDK и видимую NVIDIA ICD. Для конвертации нужен NumPy, для независимого эталона также PyTorch и Transformers. Для CLI `hf` нужен пакет huggingface_hub. Начните из корня checkout этого коммита, выберите новый каталог и подстройте маску физических ядер под машину.

```bash
work=$(mktemp -d)
hf download TinyLlama/TinyLlama-1.1B-Chat-v1.0 \
    --revision fe8a4ea1ffedaf415f4da2f062534de366a451e6 \
    --include model.safetensors config.json --local-dir "$work/snapshot"
python3 tools/prepare_session_weights.py "$work/snapshot" "$work/tinyllama.w8"

# Одинаковый публичный W8A8 путь и runner в обеих сборках.
git worktree add --detach "$work/stock" HEAD
git -C "$work/stock" restore --source=6fa401e0 -- velri-lib/cmake/slang.cmake \
    velri-lib/src/backend/cpu/w8a8_gemv.h velri-lib/src/backend/vulkan velri-lib/src/kernels/slang/vk
cmake -S "$work/stock" -B "$work/before" -G Ninja -DCMAKE_C_COMPILER=clang \
    -DCMAKE_BUILD_TYPE=Release -DVELRI_BUILD_BENCHMARKS=ON -DVELRI_ENABLE_VULKAN=ON
cmake -S . -B "$work/after" -G Ninja -DCMAKE_C_COMPILER=clang \
    -DCMAKE_BUILD_TYPE=Release -DVELRI_BUILD_BENCHMARKS=ON -DVELRI_ENABLE_VULKAN=ON
cmake --build "$work/before" --target bench_session profile_session
cmake --build "$work/after"
export VK_DRIVER_FILES=/usr/share/vulkan/icd.d/nvidia_icd.json
ctest --test-dir "$work/after" --output-on-failure
python3 tools/compare_decode64.py "$work/before/bench_session" "$work/after/bench_session" \
    "$work/tinyllama.w8" "$work/runs" --cpus 0-15 --workers 16
for device in avx2 avx512 vulkan; do
    python3 tools/check_session_reference.py "$work/snapshot" "$work/runs/$device-after-1.f32" --device cuda
done
```

SHA-256 исходного `model.safetensors` — `6e6001da2106d4757498752a021df6c2bdc332c650aae4bae6b0c004dcf14933`, файла `tinyllama.w8` — `4a42c4e05fffc0cbe3cadf1fad19412ee09ecea6595053eedc12cfc970081002`. Протокол сравнения с его исходными потолками был записан до оптимизации, SHA-256 `1b29e60e3fee41dcfcdb99c2a22c13e9304ffec4ff4052e59a227b0a80df3bf3`. Для первой сборки в параметре `--vk-header` укажите заголовок из `$work/stock`, если пересчитываете пооператорную таблицу вручную. [Команды профилирования](../../../tools/profile/README.md)
