# Как повторить замеры на 16 384, 32 768 и 65 536 токенах

В каждом замере одна последовательность. Движок с пустым KV обрабатывает весь промпт чанками по 1024 токена, затем выполняет 32 одиночных шага decode. Стенд измеряет Velri CPU/Vulkan и llama.cpp CPU/CUDA/Vulkan на одном GGUF.

## Сборка и запуск

Для сборки нужны Linux x86-64, CMake, Ninja, Clang с C23, C++17, Slang `slangc`, заголовки и загрузчик Vulkan. Для библиотек llama.cpp нужны исходники ревизии `8d60873dfb8619f2b5ed31adfbab07cccb40db5c`, Vulkan SDK с `glslc` для Vulkan и CUDA Toolkit для CUDA. Для запуска нужны Python 3 с NumPy, `taskset` из util-linux и NVIDIA-драйвер с `libnvidia-ml.so.1`. Измеритель требует доступ к спискам GPU-процессов NVML и при CPU-прогоне, чтобы подтвердить нулевое потребление VRAM.

Скрипт сборки использует две готовые Ninja-сборки Velri Release с `BUILD_TESTING=ON` и локальным `velri-lib`. В одной задано `VELRI_ENABLE_VULKAN=OFF`, во второй — `ON`. В каждой достаточно собрать цель `test_engine_runtime`. Для llama.cpp используются две Release-сборки с `BUILD_SHARED_LIBS=ON`, `GGML_NATIVE=ON`, `GGML_BACKEND_DL=OFF` и `GGML_BLAS=OFF`. В первой включён только Vulkan из двух GPU-бэкендов, во второй только CUDA (архитектура 120 для RTX 5070 Ti). Укажите каталоги с `libllama.so`, `libggml.so`, `libggml-base.so` и их зависимостями. CPU-стенд llama.cpp загружает первую сборку с отключённой регистрацией Vulkan и проверяет наличие единственного устройства CPU. [Сборка стендов](build.py) · [CPU-стенд llama.cpp](llama-cpu.cpp)

Сначала сгенерируйте контрольный GGUF по инструкции ниже. Пример использует общую рабочую папку `WORK`. Расположения исходников llama.cpp, готовых библиотек и модели можно переопределить переменными окружения. Velri использует индекс фиксированных смещений для этого конкретного GGUF. Проверка SHA-256 защищает от подстановки другого файла такой же длины. [Генерация GGUF](weights/README.md) · [Индекс тензоров](gguf_index.h)

```sh
repo=$(git rev-parse --show-toplevel)
harness="$repo/docs/benchmarks/2026-11-22-long-context/harness"
WORK=${WORK:-"$HOME/.cache/velri-long-context"}
VELRI_CPU_BUILD=${VELRI_CPU_BUILD:-"$WORK/velri-cpu"}
VELRI_GPU_BUILD=${VELRI_GPU_BUILD:-"$WORK/velri-vulkan"}
LLAMA_SRC=${LLAMA_SRC:-"$WORK/llama.cpp"}
LLAMA_VULKAN_LIB=${LLAMA_VULKAN_LIB:-"$WORK/llama-vulkan/bin"}
LLAMA_CUDA_LIB=${LLAMA_CUDA_LIB:-"$WORK/llama-cuda/bin"}
MODEL=${MODEL:-"$WORK/velri-llama-f32.gguf"}
python="$WORK/venv/bin/python"
printf '%s  %s\n' e0e76115155be432eb30ab5e623d8acc9b4ab6b97f47ad2cda3eb2ea19ed8453 "$MODEL" | sha256sum -c - || exit 1

"$python" "$harness/build.py" \
  --velri-cpu-build "$VELRI_CPU_BUILD" \
  --velri-gpu-build "$VELRI_GPU_BUILD" \
  --llama-src "$LLAMA_SRC" \
  --llama-vulkan-lib "$LLAMA_VULKAN_LIB" \
  --llama-cuda-lib "$LLAMA_CUDA_LIB" \
  --out "$WORK/bin"

taskset -c 31 "$python" -u "$harness/run.py" \
  --bin "$WORK/bin" --model "$MODEL" --out "$WORK/results" --snap "$WORK/logits" \
  --engines velri-cpu-f32 llama-cpu-f32 \
            velri-vulkan-f16kv llama-cuda-f16kv llama-vulkan-f16kv \
            velri-vulkan-f32 llama-cuda-f32 llama-vulkan-f32

"$python" "$harness/summarize.py" "$WORK/results"
```

По умолчанию запускаются все три длины и три повтора в отдельных процессах. Для одной длины или повтора добавьте, например, `--lengths 32768 --blocks 2` к команде `run.py`. Процессы стендов разделяют блокировку `/tmp/velri-gap-gpu.lock`. Готовый JSON пропускается при перезапуске, поэтому после смены бинарников или модели выбирайте новый каталог результатов. Для CPU на Ryzen 9 9950X выделены 16 рабочих потоков с привязкой к CPU 0–15 (по одному потоку на физическое ядро). Для GPU задан один рабочий поток с той же маской, а для монитора — логический CPU 31. На другой топологии маски нужно адаптировать в команде и в скрипте. [Параметры запуска](run.py)

## Модель и точность

Синтетическая Llama содержит 62 927 616 параметров в 75 F32-тензорах (240,05 МиБ весов). У неё 8 слоёв, ширина 768, SwiGLU 2048, 12 Q-голов и 4 KV-головы размерности 64, словарь 8192. В GGUF указан контекст 9216. Для всех трёх промптов позиции продолжаются с исходным RoPE (`theta=10000`, без масштабирования). Эти замеры проверяют вычислительную стоимость за пределами указанной длины. [Дескриптор Velri](velri-gpu.c) · [Параметры GGUF](weights/README.md)

| Профиль | Размещение и арифметика |
|---|---|
| CPU F32 | Оба движка хранят веса и KV на CPU в F32. У llama.cpp отключены Flash Attention и offload. |
| GPU F16 KV | Все веса на GPU в F32, постоянный KV в F16. Velri использует F16-операнды проекций и attention с накоплением в F32. llama.cpp использует нативную арифметику и Flash Attention. |
| GPU F32 | Весам и KV задан F32. У Velri настройки точности префилла равны 32. У llama.cpp отключён Flash Attention, для CUDA принудительно выбран F32 в cuBLAS и отключён TF32. Для Vulkan отключены FP16 и кооперативные матрицы, но в этой ревизии отдельные операции с разрывным шагом могут округлять операнды до F16. |

Параметры контекста и размещения задают стенды каждого движка. Настройки библиотек и переменные окружения выставляет скрипт запуска. [Velri Vulkan](velri-gpu.c) · [llama.cpp GPU](llama-gpu.cpp) · [Скрипт запуска](run.py)

## Что входит в результат

Для промпта длины `N` ёмкость KV равна `N+256` (16 640, 33 024 и 65 792). У llama.cpp `n_batch=n_ubatch=1024`. Перед измерением каждый процесс трижды обрабатывает 4096 токенов и 32 шага decode с той же ёмкостью KV. Перед каждой следующей итерацией KV сбрасывается. Входной токен на позиции `i` равен `(37*i+11)%8192`. Все движки получают одни и те же 32 продолжения по этой формуле, независимо от их предсказаний.

На каждом вызове API движок возвращает на CPU полную строку из 8192 логитов последнего токена чанка. Таймер префилла охватывает все чанки и жадный выбор после последнего. На decode каждый таймер охватывает один шаг со своим жадным выбором. Загрузка модели, подготовка, прогрев и сохранение снимков выполняются за пределами этих таймеров. Скорость префилла равна `N / время префилла`, скорость decode — `32 / суммарное время 32 шагов` (время в секундах). [Velri](velri-gpu.c) · [llama.cpp](llama-gpu.cpp)

RAM — пиковый RSS всего процесса за время его жизни по Linux `wait4(ru_maxrss)`, включая резидентные страницы отображённых файлов. VRAM — максимум, наблюдавшийся для этого PID на устройстве NVIDIA 0 через NVML. Опрос охватывает загрузку, прогрев, измерение и выход. Запрашиваются списки compute и graphics с паузой 10 мс между опросами. Одинаковое выделение не суммируется дважды. Короткий пик может попасть между опросами. Фактический максимальный интервал записан в `max_observed_poll_gap_ms`. [Измеритель памяти](memory.py)

В `results/records/` каждый процесс оставляет CSV с временами 33 фаз, журнал и сжатую трассу NVML. Успешный прогон добавляет JSON с TPS, пиками памяти и хешами бинарника и логитов. В `logits/` лежат 33 строки F32 по 8192 числа. Стенд проверяет конечность значений и совпадение записанного greedy ID с argmax каждой строки. Независимая проверка точности на длинном контексте потребовала бы отдельного эталона. В `samples.csv` виден статус каждого повтора, в `summary.csv` каждая метрика получает медиану только при наличии всех трёх успешных прогонов. [Проверки вывода](run.py) · [Расчёт медиан](summarize.py)
