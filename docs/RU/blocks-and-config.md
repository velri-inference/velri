# Блоки моделей и конфигурация размещения

[English](../EN/blocks-and-config.md)

Этот документ описывает две взаимосвязанные части уровня движка Velri: как архитектуры собираются из переиспользуемых блоков поверх операций `velri-lib`, и как JSON-конфигурация управляет размещением этих компонентов по устройствам.

**Статус:** целевая спецификация C-движка. Примеры целевой схемы лежат в [examples/example-dense.json](../../examples/example-dense.json) и [examples/example-moe.json](../../examples/example-moe.json).

---

## 1. Уровни композиции модели

| Уровень | Примеры | Что задаётся |
| :--- | :--- | :--- |
| **Операция** (`velri-lib`, `graph.h`) | `Linear`, `BatchedLinear`, `RMSNorm`, `LayerNorm`, `RoPE`, `Attention`, `GDN`, `FWHT` | Формула, формы/типы входов и выходов, чтения/записи состояния |
| **Переиспользуемый блок и общий слой** (`velri-lib`, `blocks.h`) | `velri_builder`, `velri_manifest`, `norm`, `linear`, `embedding`, `attention_core`/`dense`/`latent`, `mlp`, `lm_head`, общий `pre_norm` | Подграфы без привязки к имени семейства и без хардкода скоупов конфига |
| **Движковые хелперы слоёв** (`Velri`, `src/model/layers.{h,c}`) | `velri_model_params`, `velri_pre_norm_layer_desc`, `velri_lm_head_desc`, скоупы размещения (`input-layer`, `hidden-layers`, `attention`, `kv-cache`, `dense-mlp`, `lm-head`) | Привязка метаданных модели и JSON-скоупов размещения к блокам `velri-lib` |
| **Архитектура** (`Velri`, `src/model/arch/`) | `GPT-2`, `Llama`, `Qwen3.5`, `Qwen3.8-Flash-Next`, `Gemma 4` | Полная схема слоёв, сопоставление весов, дополнительные ветви (`PLE`, `MTP`, энкодеры) |

Повторное использование блока означает повторное использование **описания вычислений**: веса и состояние не становятся общими автоматически — совместное владение всегда объявляется явно.

### Пример: `GatedMLP` отдельно и внутри `MoE`

```text
input ──► Linear(gate) ──► Activation ──┐
                                        × ──► Linear(down) ──► output
input ──► Linear(up)   ─────────────────┘
```

Тот же блок работает и как плотный FFN, и как отдельный эксперт внутри `MoE`: роутер выбирает `top-k` экспертов, передаёт им входы и объединяет результаты снаружи, не меняя внутренности `GatedMLP`.

### Пример: гибридная архитектура (`GDN` + `QSA`)

```text
gdn_layer = Layer(
    mixer = GDN(...),
    ffn   = MoE(router, experts = GatedMLP(...)),
    connections = HyperConnections(...)
)

qsa_layer = Layer(
    mixer = Attention(projections, position_transform, QSASelection(...), core),
    ffn   = MoE(router, experts = GatedMLP(...)),
    connections = HyperConnections(...)
)

layers = Repeat([gdn_layer, gdn_layer, gdn_layer, qsa_layer], count)
```

Это иллюстрация композиции (не финальный C API). Условий вида `if (family == GEMMA4)` внутри общих блоков нет: все отличия — в явном составе операций, параметрах и ссылках на ресурсы.

### Разложение attention и хранение состояния

В описании attention разделяются пять независимых аспектов:
1. **Получение `Q`, `K`, `V`** (проекции, чтение сохранённого буфера или вывод одного из другого).
2. **Позиционное кодирование** (`RoPE`, частичный `p-RoPE`, 3D `M-RoPE`).
3. **Выбор доступной истории** (полный контекст, скользящее окно, разреженный индексер `QSA` или `DSA` — одного флага `sparse` недостаточно; работа индексера учитывается отдельно).
4. **Расчёт внимания** (масштаб, маски, `softcap`, обучаемые синки).
5. **Хранилище состояния** (см. [роли K/V в архитектуре Velri-lib](../../velri-lib/docs/RU/architecture.md#3-память-представления-и-роли-kv)): отдельные буферы, общий буфер, хранение только `V` с восстановлением `K = RoPE(V * w_k)` или рекуррентное состояние `GDN`.

### Чеклист добавления новой модели
1. Выписать точные формулы, параметры, состав весов и состояние (см. примеры в [models/README.md](models/README.md)).
2. Реализовать чтение метаданных и сопоставление имён весов в адаптере семейства.
3. Собрать схему слоёв и ветвей из готовых блоков (и при необходимости добавить недостающую общую операцию + C23-эталон в `velri-lib`).
4. Сверить логиты и эволюцию состояния с независимой реализацией на нескольких шагах, включая эквивалентность prefill и пошагового decode, а также отсутствие лишних выделений памяти.

## 2. Целевая JSON-конфигурация размещения

Конфигурация читается один раз при загрузке через встроенный zero-dependency C23 потоковый JSON-сканер (`src/format/json.{h,c}`), валидируется и превращается в плоский план размещения (`src/config/placement.{h,c}`). Кернелы JSON не видят.

### Поля размещения и устройства
В любом узле дерева модели допускаются три наследуемых поля:
- **`store`** — где постоянно хранятся данные;
- **`compute`** — на каком устройстве выполняется decode (и prefill по умолчанию);
- **`prefill-compute`** *(опционально)* — отдельное устройство для стадии prefill.

Имена вычислительных устройств имеют вид `<бэкенд>:<индекс>` и проверяются по [реестру бэкендов](../../velri-lib/docs/RU/architecture.md#5-реестр-бэкендов-и-общий-контракт) без хардкода в парсере:

| Значение | Смысл |
| :--- | :--- |
| `cpu:0` | Вычислительный контекст CPU |
| `vulkan:0` | Вычисления (`compute`) или хранилище (`store`) на выбранном Vulkan-устройстве |
| `ram:0` | Хранилище в памяти хоста (только для `store`, не вычислительный бэкенд) |
| `disk` | Файловое хранилище с явной подгрузкой и staging-буферами (только для `store`) |

Индекс привязывается к конкретному устройству при запуске и выводится в `inspect`. Устаревшие значения `cuda:N` / `vram:N` (из прежних прототипов) и неоднозначное `device:0` не конвертируются молча — парсер возвращает явную ошибку с подсказкой миграции.

### Каскадное наследование и селекторы слоёв
1. Вниз по дереву модели наследуются только `store`, `compute` и `prefill-compute`.
2. Внутри `hidden-layers` допустимы селекторы слоёв вида `"N"` и `"N-M"` (или через запятую), содержащие то же поддерево компонентов.
3. **Приоритет (от высшего к низшему):**
   - самый глубокий узел внутри совпавшего селектора слоёв (например, `hidden-layers → "32-47" → moe → routed-experts`);
   - самый глубокий узел в общем `hidden-layers`;
   - значения по умолчанию в корне `model`.
4. **Валидация:** пересекающиеся селекторы и опечатки в ключах отклоняются; известные компоненты, отсутствующие у данной модели, отмечаются в `inspect` как неприменимые; выход селектора за пределы числа слоёв регулируется режимом строгости.

### Настройки бэкендов (`backends.<имя>`)
Настройки конкретного бэкенда располагаются на верхнем уровне в секции `backends.<имя>`, через дерево модели не наследуются и валидируются самим модулем бэкенда в `velri-lib` при создании контекста.

```json
{
  "model": {
    "path": "models/qwen3.8-flash-next",
    "store": "vulkan:0",
    "compute": "vulkan:0",
    "hidden-layers": {
      "moe": {
        "routed-experts": {
          "store": "ram:0",
          "compute": "cpu:0",
          "prefill-compute": "vulkan:0"
        }
      }
    }
  },
  "backends": {
    "cpu": {
      "threads": 0,
      "reserve-cores": 1,
      "affinity": "auto"
    },
    "vulkan": {
      "prefill-chunk-size": 4096
    }
  }
}
```

- `cpu.threads: 0` выбирает число рабочих потоков по доступным процессу физическим ядрам за вычетом `reserve-cores` (логические SMT-потоки не выдаются за физические ядра).
- `cpu.affinity`: `"auto"` (закрепить по возможности, иначе объяснить причину), `"none"` (без привязки) или `"required"` (ошибка при невозможности закрепить).
- Полные примеры целевой схемы для плотной и MoE-модели: [examples/example-dense.json](../../examples/example-dense.json) и [examples/example-moe.json](../../examples/example-moe.json).

### Разделение парсинга и проверки возможностей
То, что конфиг валиден синтаксически, ещё не гарантирует, что устройство поддерживает нужные операции, типы и передачи данных. Проверка возможностей, пересылок и бюджета памяти выполняется на этапе `prepare`. Неизвестный бэкенд, выключенный при сборке бэкенд и отсутствие подходящего устройства дают различимую диагностику; `inspect` показывает запрошенное размещение, итоговое разрешение и источник каждого правила.
