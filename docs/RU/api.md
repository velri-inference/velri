# Внешний C API и приложения Velri

[English](../EN/api.md)

Этот документ описывает целевой публичный **C23 API движка Velri** (`include/velri/`) и планируемые приложения поверх него. Внутренние вычисления, бэкенды и графы принадлежат `velri-lib` ([velri-lib/docs/RU/architecture.md](../../velri-lib/docs/RU/architecture.md)); `Velri` предоставляет уровень моделей, сеансов и генерации.

**Статус:** базовый публичный C23 API движка ([`include/velri/velri.h`](../../include/velri/velri.h)) и рантайм (`src/runtime/{context,model,program,session,sampler}.c`) — включая `Context`, `Model`, единый и двухплановый `Program` без дублирования памяти, `Session`, отмену и семплирование без аллокаций — реализованы и покрыты тестом `engine_runtime`. Загрузчик `.vtq`, токенизатор, чат-шаблоны и CLI/HTTP-приложения запланированы далее.

---

## 1. Основные объекты C API

Вычислительный движок используется библиотекой напрямую, без зависимости от CLI, HTTP-сервера, токенизатора или чат-шаблонов. В минимальном режиме приложение передаёт `token IDs`, вызывает шаг исполнения и получает логиты либо выбранные токены.

Долгоживущие объекты представлены непрозрачными C-дескрипторами с парными функциями создания и освобождения:

| Объект | Ответственность и время жизни |
| :--- | :--- |
| `Context` | Владеет контекстом устройств `velri-lib`, пулом CPU и платформенными ресурсами. Должен жить дольше всех зависимых объектов |
| `Model` | Хранит конфигурацию, веса и неизменяемые подготовленные представления. Разделяется между несколькими сеансами |
| `Program` | Хранит проверенный и подготовленный план исполнения для конкретных `Model`, `Context` и лимитов нагрузки |
| `Session` | Хранит изменяемое состояние последовательности (историю, кэши/GDN) и выделенные рабочие слоты |

Попытка уничтожить объект, от которого ещё зависят живые объекты (например, `Context` при живом `Session`), возвращает явную ошибку. В публичные заголовки не попадают типы `VkBuffer`, Slang, SIMD или сторонних зависимостей. Стабильный бинарный ABI на первом этапе не обещается.

Для настройки общего пула CPU из `backends.cpu` используйте `velri_ctx_create_from_json`. Функция принимает полный конфиг или объект только с секцией `backends` и возвращает диагностику в буфере вызывающего кода. Ненулевой `velri_ctx_options.cpu_threads` и явно заданный `threads` в JSON должны совпадать. Полный конфиг передаётся в `velri_program_prepare` для размещения модели и выбора лимитов. На этом этапе можно опустить настройки CPU или указать тот же режим выбора потоков и тот же резерв для автоматического режима. При конфликте возвращается `VELRI_RC_ERR_INVALID`. Поле `velri_device_info.cpu_workers` для CPU показывает фактическое число рабочих потоков, включая вызывающий поток.

Веса регистрируются по каноническому имени. Привязка веса требует исключительного доступа к реестру. При одновременной привязке или подготовке программы один из вызовов может вернуть `VELRI_RC_ERR_BUSY`. Привязки остаются неизменными до уничтожения всех программ, использующих модель.

## 2. Владение буферами, синхронность и параллелизм

Веса можно привязать прямо к доступному только для чтения отображению неизменяемого файла. Отображение должно оставаться действительным до уничтожения модели и её программ. В Linux после успешной загрузки на GPU вызывающая сторона может освободить резидентные страницы чистого отображения через `madvise(MADV_DONTNEED)`. При следующей подготовке они снова загрузятся из того же файла. Это подходит для принадлежащих вызывающей стороне, выровненных по странице областей, к которым CPU в ближайшее время обращаться не будет.

- Для каждого буфера API явно фиксирует владельца и срок жизни.
- **Первый вариант `step` — синхронный:** входной буфер вызывающего кода живёт до возврата из вызова; возвращённый заимствованный срез результата действителен до следующей изменяющей операции над сеансом или его уничтожения. Внутри синхронного вызова бэкенды `velri-lib` могут исполнять задания асинхронно.
- Если позже потребуется асинхронный `step`, он получит отдельный объект завершения и собственные правила удержания буферов.
- В одном `Session` одновременно может выполняться только один шаг. Разные сеансы имеют независимое состояние и координируются через общий `Context`; потокобезопасность каждой функции явно документируется в заголовках.

## 3. Ошибки и отмена

- Все функции возвращают код статуса (неверные аргументы, неподдержанная операция, нехватка памяти/ёмкости, ошибка I/O, ошибка устройства) и сохраняют диагностический контекст. Библиотека не вызывает `abort`/`exit` и не использует `longjmp` через код приложения.
- Размеры, смещения и переполнения проверяются до начала записи.
- При отмене или ошибке во время уже начавшегося шага применяются правила безопасности ресурсов из [velri-lib/docs/RU/execution.md](../../velri-lib/docs/RU/execution.md#4-завершение-ошибки-и-отмена):
  - память не освобождается, пока не завершены все принятые работы устройств;
  - приложение различает нормальную остановку (`stop`), отмену по запросу и ошибку;
  - отмена после принятия первой работы шага или ошибка, затронувшая состояние, требуют явного `reset` сеанса (автоматический откат частичного шага в первой версии не обещается).

## 4. Токенизатор и чат-шаблоны

Токенизатор и форматирование диалога реализуются как отдельные адаптеры поверх вычислительного ядра и проверяются независимо друг от друга:
- токенизатор сверяется по точным `token IDs`, специальным токенам, нормализации Unicode, byte fallback и потоковому декодированию;
- чат-шаблон проверяется отдельно; неподдержанный шаблон никогда не подменяется приближённым молча (только по явному флагу пользователя);
- на выходе метаданные модели разделяют события текста, рассуждений (`reasoning`) и вызовов инструментов (`tool calls`).

## 5. Планируемые CLI и HTTP/SSE

| Команда | Назначение |
| :--- | :--- |
| `inspect` | Показать доступные бэкенды и устройства, запрошенное и разрешённое размещение, применённые настройки и доступный расчёт памяти |
| `run`, `chat` | Запуск генерации или интерактивного диалога поверх C API |
| `probe`, `bench` | Замер оборудования, отдельных операций и полного шага модели с сохранением условий |
| `pack` | Автономная перепаковка весов с явной версией формата раскладки |
| `quantize` | Отдельный инструмент калибровки и квантования весов |
| `serve` | Необязательный HTTP/SSE-сервер поверх runtime |

HTTP-сервер транслирует запросы в команды runtime, ограничивает очереди запросов и выходных событий (применяя backpressure или отмену при медленном клиенте) и при отключении клиента инициирует отмену с корректным ожиданием завершения работ устройств.
